# 근거 기반 포트폴리오 관리 설계

설계 기준은 `master`의 `5327470`이다. 첫 출시 범위 0~3을 구현했으며 실제 명령은 저장소 README를 따른다. 이 문서는 설계 판단과 후속 범위를 보존한다. [검토 채팅](codex://threads/01a1aa16-7663-74c2-af5f-5b6c5b95f32a)의 제품 검토, P0 설계, 단계별 작업 목록을 반영한다.

첫 출시의 목표는 **프로젝트 선택 → 본인 기여와 근거 확인 → 소개문 내보내기 → 재수집 후 변경 검토**를 완주하는 것이다. 직무별 공고 연결과 외부 모델은 이 흐름이 안정된 뒤 추가한다. 기존 채팅의 넓은 P0를 전체 제품 로드맵으로 유지하되 첫 출시 판정은 이 작은 흐름에 둔다.

## 현재 코드와 추가로 필요한 계약

현재 `run`은 활동 원본을 고유키로 병합하고, 활성 단계가 성공하면 출력 디렉터리를 교체한다. 단계별 기준 시각은 실행 시작 시점이다. 이 변경은 기록 손실을 막지만, 개별 항목을 이번에 다시 조회했는지는 표현하지 않는다.

- [storage.py](../../../acta/storage.py)는 누적 캐시와 출력 게시를 관리한다. `.records/`는 현재 내부 저장 형식이며 소비자용 버전 계약이 아니다.
- [cli.py](../../../acta/cli.py)는 기준 시각과 범위를 기록한다. 보존된 과거 PR을 이번 실행에서 확인했다고 해석할 수는 없다.
- 저장소는 이름과 URL, 커밋은 전체 OID를 갖는다. 프로젝트와 PR의 원격 고정 ID는 수집 계약에 추가해야 한다.
- [analyzer.py](../../../acta/analyzer.py)는 원본 파일을 조합하고 정해진 분석 파일명에 쓴다. 검토된 포트폴리오 문서의 저장·생성 경로로 재사용하지 않는다.
- [resume 템플릿](../../../acta/templates/resume.md)은 수치를 필수로 요구하고 커밋 수로 정렬한다. [profile 템플릿](../../../acta/templates/profile.md)은 별표 저장소에서 도구 사용을 추론한다. 우선 수정할 표현 규칙이다.

기존 `run`, `deep`, `analyze`, MCP의 호환성을 유지한다. `analyze` 결과는 미검토 초안이며 포트폴리오 확인 기록을 자동으로 얻지 않는다.

## 사용자 흐름

다음은 첫 출시의 명령 흐름이다. `--workspace`를 생략할 때는 현재 디렉터리의 `./portfolio`만 사용한다. 상위 디렉터리나 다른 작업 공간을 자동 탐색하지 않는다.

```bash
acta run --days 365
acta portfolio init --source ./acta_data --workspace ./portfolio
acta portfolio projects
acta portfolio select <project-id> --reason "플랫폼 직무와 관련"
acta portfolio claim edit --project <project-id>
acta portfolio claim review <claim-id>
acta portfolio draft create --project <project-id>
acta portfolio draft edit <draft-id>
acta portfolio draft review <draft-id>
acta portfolio export <draft-id> --audience public --output ./exports

acta run --since-last-run
acta portfolio refresh
acta portfolio review
```

`claim edit`는 문제, 본인 역할, 행동, 결과와 선택한 근거를 편집기로 보여준다. 검토 화면은 개인 기여와 팀 성과를 구분하고 발췌·원문·관찰 시점·공개 범위를 함께 보여준다. 수치가 없어도 정성적 결과로 저장하고 확인할 수 있다. GitHub 외 프로젝트는 `acta portfolio add-project --name "프로젝트명"`으로 추가한다. `claim edit`에서 수동 근거를 입력할 수 있다.

`refresh`는 기본적으로 로컬 수집 결과만 읽는다. `refresh --probe-selected`를 명시하면 사용자가 연결한 원격 근거만 다시 조회한다. 조회 실패나 접근 불가는 기존 내용과 사용자 편집을 삭제하지 않는다.

```mermaid
flowchart LR
    C[수집기 소유 데이터] --> S[버전 있는 단일 입력 파일]
    S --> P[포트폴리오 작업 공간]
    U[사용자 역할·주장·확인] --> P
    P --> V[문장별 근거·공개 범위 검증]
    V --> E[소개문과 공개 가능한 근거 목록]
```

## 수집기와 포트폴리오의 연결

수집기가 `acta_data/portfolio-source.json` 한 파일을 기존 임시 출력 안에 생성한다. 포트폴리오는 이 파일을 한 번 열어 읽은 바이트를 검증하고 가져온다. 파일이 게시 중 일시적으로 보이지 않으면 제한적으로 재시도한 뒤 쓰기 없이 종료한다. 여러 캐시 파일을 각각 읽어 서로 다른 실행 결과를 섞지 않는다.

입력의 주요 필드는 다음과 같다.

| 필드 | 계약 |
|---|---|
| `schema_version`, `snapshot_id` | 지원 버전과 가져오기 중복 판정에 사용한다. 동일 ID에 다른 내용이 오면 오류다. |
| `subject`, `generated_at` | 제공자, 계정 식별자, 수집 결과 생성 시각이다. 항목별 관찰 시각을 대신하지 않는다. |
| `coverage` | 단계별 조회 필터·기간, 완료·건너뜀 상태, 페이지 순회 완료 여부다. 전체 GitHub 활동의 완전성을 의미하지 않는다. |
| `projects`, `resources` | 프로젝트 후보와 정규화된 최신 보유 내용이다. 각 항목에 출처·공개 여부·마지막 성공 관찰 시각을 포함한다. |
| `observations` | 이번 실행에서 실제로 조회한 항목의 결과다. 캐시 재출력은 새 관찰이 아니다. |

자료의 상태는 다음 세 축으로 분리한다.

| 축 | 값과 처리 |
|---|---|
| 관찰 결과 | `observed`, `not_resolvable`, `not_observed`, `failed` |
| 내용과 시점 | 마지막 정상 내용, 마지막 성공 관찰 시각, 마지막 조회 시도, 현재 입력이 새 관찰인지 보존 캐시인지 |
| 사용자 검토 | `draft`, `confirmed`, `needs_review`, `rejected`를 버전과 확인 기록에서 계산 |

증분 결과에 항목이 없으면 `not_observed`다. 403이나 404를 직접 받으면 접근 불가 또는 찾을 수 없음인 `not_resolvable`이며 삭제라고 단정하지 않는다. 시간 초과·서비스 오류는 `failed`다. 모두 마지막 정상 내용을 보존한다. 전체 수집 실패는 새 성공 입력 파일을 게시하지 않는다. 선택 근거 조회 실패는 해당 시도의 실패로만 기록한다.

정상 관찰에서 의미 있는 내용이 바뀌면 연결된 주장과 문장을 재검토 대상으로 보여준다. 건너뜀·범위 밖·조회 실패만으로 내용 변경이나 갱신 성공을 만들어내지 않는다. 이미 확인한 과거 기록은 확인 당시의 자료로 남고, 화면과 근거 목록에 마지막 관찰 시점을 표시한다. 현재 상태를 새로 확인했다는 보장은 별도 조회가 성공했을 때만 표시한다.

원격 식별자는 `provider + node_id`, 커밋은 `repository_node_id + full_oid`를 사용한다. `owner/name`과 URL은 위치 정보다. GitHub의 [global node ID 조회](https://docs.github.com/en/graphql/guides/using-global-node-ids)를 사용하되 ID 형식 변경도 별칭으로 다룰 수 있게 한다. 사용자 작업 공간의 ID는 별도 UUID로 유지한다.

이전 출력은 명시적 이관 어댑터로 읽는다. ID나 관찰 시점이 없으면 `provisional`, `unknown`을 유지한다. 선택된 근거를 성공적으로 조회한 뒤 고정 ID에 연결한다. 같은 이름만으로 다른 저장소를 합치지 않는다. 잘못된 계정·지원하지 않는 상위 버전·충돌하는 ID는 가져오기 전에 거절한다.

## 저장 구조와 소유권

포트폴리오의 정본은 별도 `portfolio/workspace.sqlite3`에 둔다. 첫 구현은 객체와 변경 불가능한 이력을 한 JSON 집합으로 저장하고 SQLite 트랜잭션으로 갱신한다. 관계 검증은 작업 공간 모듈이 담당하며 별도의 ORM이나 객체별 SQL 테이블은 추가하지 않는다. Python 표준 `sqlite3`를 사용한다. 수집기는 이 DB에 쓰지 않고, 포트폴리오는 수집 캐시에 쓰지 않는다. 내보낸 Markdown은 파생 산출물이다.

| 객체 | 필수 내용 |
|---|---|
| Project | 고정 ID, 원격 별칭 또는 수동 출처, 사용자 이름·설명, 선택과 이유 |
| EvidenceRevision | 프로젝트, 원격 또는 수동 출처, 선택 필드·발췌, 내용 지문, 관찰 참조, 공개 판단 |
| ClaimRevision | 개인·팀 범위, 본인 역할, 문제·행동·결과, 근거 버전 연결, 선택적 측정 자료 |
| Confirmation | 확인한 주장 버전, 근거 버전 집합, 공개 판단과 규칙 버전의 지문, 확인 주체와 시각 |
| DraftRevision | 이전 버전, 문장 블록, 블록별 정확한 주장 버전 연결, 편집된 본문 |
| BlockConfirmation | 검토한 블록 본문과 주장 연결의 지문, 검토 시각 |
| Observation | 입력 ID, 출처 ID, 조회 결과, 마지막 정상 내용 참조와 실제 관찰 시각 |

각 객체의 변경은 새 버전을 만든다. 프로젝트 선택 이유, 사용자 역할, 초안 편집본은 수집 내용으로 덮어쓰지 않는다. 수동 근거는 자기 보고로 표시하며 독립적 검증으로 표현하지 않는다.

확인 기록은 `claim_id`에만 붙이지 않는다. **정확한 본문·역할·근거 버전·공개 판단**에 붙인다. 새 버전은 이전 확인을 자동 승계하지 않는다. 주장, 초안, 검토 목록에 변경 상태를 각각 저장하지 않고 같은 참조 비교로 계산한다. 명시적 거절 결정은 별도로 보존한다.

내용 지문은 검토에 사용한 제목·본문·병합 상태·선택 발췌와 그 선택 규칙으로 만든다. `fetched_at`, 별 수, 표시용 URL 변경만으로 본인 기여 내용을 변경 처리하지 않는다. 원격 공개 여부 변경은 내용과 별개로 공개 정책의 재검토 사유다.

측정 자료는 `value`, `unit`, `period`, `method`, `evidence_revision_ids`로 구성한다. 개선 비교에는 기준값과 비교 조건도 필요하다. 필수 설명이 없으면 측정된 개선으로 확인하지 않는다. 자유 문장의 숫자를 정규식으로 검사해 진위를 판정한다고 약속하지 않는다. 확인은 사용자의 사실관계 검토 기록이다. 이력서는 사실을 정량 또는 정성적으로 표현할 수 있다. [Harvard 이력서 가이드](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/)

쓰기 작업은 짧은 SQLite 트랜잭션과 예상 revision 비교로 묶는다. 편집기와 네트워크 호출은 트랜잭션 밖에서 실행한다. 두 세션이 같은 버전을 편집하면 먼저 저장한 작업만 적용하고 나중 저장에는 충돌과 편집 원문을 돌려준다. DB 행·SQL·GitHub 응답 dict를 도메인 밖으로 노출하지 않는다. 백업은 SQLite backup API를 사용한다.

SQLite는 연결 간 미완료 변경을 숨기고 쓰기를 직렬화한다. [공식 격리 설명](https://www.sqlite.org/isolation.html)과 [원자적 커밋 설명](https://www.sqlite.org/atomiccommit.html)을 바탕으로 선택한 구조다. SQLite와 파일시스템 내보내기가 하나의 트랜잭션이라는 보장은 하지 않는다.

## 초안과 공개 내보내기

초안은 확인된 주장 버전으로 만든다. 정량 결과가 없으면 숫자를 추가하지 않는다. 각 경험 문장은 주장 버전과 근거로 역추적할 수 있어야 한다. 새 초안과 본문·연결을 수정한 초안은 `draft review`에서 문장별로 확인한다. 본문이나 연결을 편집하면 해당 블록의 확인이 무효가 된다. 재생성은 새 초안 버전을 만든다.

공개 검증은 한 도메인 함수가 담당한다. 포함될 문장, 주장, 발췌와 실제로 나갈 URL·메타데이터를 모두 검사한다. 비공개나 미확인 정보는 공개 Markdown뿐 아니라 근거 manifest에서도 제외한다. 비공개 경험을 설명할 필요가 있으면 공개 가능한 내용만 따로 작성한 수동 근거를 사용자가 확인한다. 원문을 자동 익명화하거나 공개 가능으로 승격하지 않는다.

미검토 블록이 있으면 기본 내보내기는 중단하고 해당 블록과 이유를 보여준다. 사용자가 명시적으로 블록을 제외할 수 있다. 자료를 조용히 빼고 완성된 이력서처럼 내보내지 않는다. 머리말과 서식 문장은 경험 주장과 구분한다.

내보내기는 유일한 산출물 디렉터리에 `document.md`와 `evidence.json`을 준비한 뒤 디렉터리 단위로 게시한다. 문서와 manifest는 동일한 입력 revision과 공개 정책으로 만든다. 게시 직전 짧은 읽기 트랜잭션에서 관련 버전·공개 판단을 재검증한다. P0의 기본 rollback journal 모드에서 게시까지 읽기 트랜잭션을 유지해 동시에 바뀐 정책으로 결과를 내지 않는다. 충돌하면 임시 산출물을 버리고 다시 준비한다. 내보내기를 DB 갱신과 함께 원자적으로 등록해야 하는 구조는 P0에 넣지 않는다.

외부 LLM 다듬기는 후속 기능이다. 추가할 때도 정제된 동일 입력으로 정확한 전송 내용을 구성하고, 대상 서비스·모델·본문 지문을 확인한다. 새 사실은 자동 확인하지 않는다. 기존 원본 `analyze --call-api`와 검토된 포트폴리오 생성 경로를 혼동하지 않게 표시한다.

## 모듈과 호출 계약

```text
acta/collection_export.py       # 수집기가 만드는 버전 있는 단일 입력
acta/portfolio/source.py        # 입력 검증, 이전 형식, 원격 ID 해석
acta/portfolio/workspace.py     # 사용자 작업, 버전, 확인·공개 규칙
acta/portfolio/store.py         # SQLite, 트랜잭션, 스키마 이관
acta/portfolio/cli.py           # Typer와 편집기
```

CLI와 후속 MCP는 완결된 사용자 작업을 호출한다. 여러 모듈에서 검증·상태 변경·저장을 순서대로 조립하게 하지 않는다. [초기 타입·함수 초안](portfolio_contract.py)은 설계 기록이다. 실제 구현 API와 명령은 workspace.py와 README가 기준이며, `confirm_claim`과 `confirm_draft`는 검토 화면의 revision과 digest를 받는다.

```python
snapshot = source.read_snapshot(source_path)
report = portfolio.import_collection(snapshot, expected_revision)
receipt = portfolio.confirm_claim(claim_id, expected_revision, review)
plan = portfolio.prepare_export(draft_id, audience="public")
artifact = portfolio.publish_export(plan, output_path)
```

## 구현 단위와 의존성

부담은 현재 구조에서의 상대 추정이다. 개발일이나 성능을 실측한 값은 없다. 이전 채팅의 18~30일은 넓은 범위의 가정치이며 이 축소안의 일정으로 사용하지 않는다.

| 순서 | 범위 | 의존성 | 부담 | 종료 기준 |
|---|---|---|---|---|
| 0 | 숫자 강제·별표 기반 숙련 추론·커밋 수 순위 지시 수정 | 없음 | 소 | 수치 없는 기여와 관심만 있는 기술의 기대 출력 예시 확보 |
| 1 | 버전 있는 수집 입력과 고정 ID | 0과 병행 | 중 | 동일 이름, 이름 변경, 보존 캐시·새 관찰을 구분하는 fixture 통과 |
| 2 | 작업 공간, 수동 프로젝트·근거·주장, 버전 확인 | 수동 경로는 독립, 수집 연결은 1 | 중 | 재시작·동시 편집·확인 후 수정에서 사용자 내용과 버전 보존 |
| 3 | 한 프로젝트의 초안·공개 내보내기·재수집 재검토 | 1, 2 | 중~대 | 최초 내보내기 후 변경된 근거만 검토하고 다시 내보내기 |
| 4 | 공고별 요구사항 연결과 초안 | 3 | 중 | 같은 주장으로 두 공고 버전을 분리하고 미확인 기술을 남김 |
| 5 | README 소개·면접 메모, 선택적 LLM 다듬기 | 3, 직무별 자료는 4 | 중 | 사용자 편집과 근거 연결을 재사용하고 없는 답변은 질문으로 표시 |
| 6 | 검토된 자료의 MCP 읽기 | 3 이후 | 소~중 | 같은 확인·공개 정책을 재사용하고 원본 전체를 기본 노출하지 않음 |

첫 출시는 0~3을 포함한다. 네트워크 전체 재조회, 자동 프로젝트 순위, ATS 합격 확률 점수, 웹 대시보드, 원격 README 자동 게시, 포트폴리오 MCP 쓰기는 이 범위에 포함하지 않는다.

## 대안 비교와 선택 근거

독립 설계 후보 두 개를 비교했다. 별도 모델을 사용한 교차 심사는 수행하지 않았고 최종 비교는 주 에이전트가 했다. 아래 평가는 성능 측정이 아니다.

| 기준 | 단일 JSON 작업 공간 | SQLite 작업 공간 |
|---|---|---|
| 사용자 점검·Git diff | 사람이 읽고 비교하기 쉬움 | 백업과 JSON 내보내기 필요 |
| 교차 객체 버전·확인 변경 | 전체 파일 재작성과 직접 검증 | 트랜잭션으로 묶고 참조 관계 검증 |
| 두 세션 편집 | OS별 잠금·revision 비교 구현 필요 | 트랜잭션·revision 비교 사용 |
| 저장 실패 처리 | 교체·동기화·잠금 복구를 직접 구현 | SQLite 커밋·복구 기능 사용 |
| 첫 출시 기능 범위 | 동일한 작은 흐름 가능 | 동일한 작은 흐름 가능 |

SQLite 후보를 기본으로 선택한다. 확인·근거·초안 사이의 변경을 함께 보존하고 두 세션의 덮어쓰기를 막는 요구가 선택 근거다. JSON 후보의 **단일 수집 입력 파일**과 **신선도와 확인의 분리**를 결합한다. 저장소 정본을 사람이 직접 편집하기보다 CLI에서 편집하고 JSON으로 점검·백업하는 비용을 받아들인다.

객체별 JSON 파일을 따로 쓰는 방식은 여러 파일을 동시에 바꾸는 복구 계약이 필요해 제외한다. 전체 이벤트 소싱·ORM·서버·벡터 DB는 현재 사용 흐름에 필요한 이점을 확인하지 못해 제외한다.

구현 시작점은 입력 fixture와 수동 프로젝트를 함께 제공하는 작업 공간이다. `source → claim → review → export → changed source → review`가 통과한 뒤 공고별 기능을 추가한다. 파일 크기나 처리 시간 때문에 저장 구조를 선택했다는 주장은 하지 않는다.
